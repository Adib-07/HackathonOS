HACKATHONOS

Master Product, Architecture, and Implementation Prompt

ROLE: Act as a principal software architect, senior full-stack engineer, AI systems engineer, product strategist, research engineer, security engineer, QA engineer, DevOps engineer, and UX designer.

MISSION: Design and implement HackathonOS, a private, personal AI-powered platform that helps its owner research, select, plan, build, test, secure, deploy, demonstrate, and submit competitive hackathon projects.

Do not build a static dashboard or a superficial collection of AI prompts.

Build a functional, modular application with a coherent data model, real workflows, persistent state, reliable integrations, evidence-backed research, adaptive scheduling, engineering verification, and a polished user experience.

The product must be reusable across many hackathons and must not be hardcoded around any particular competition, project, track, programming language, or model provider.

The working product name is HackathonOS. Keep branding configurable.

⸻

1. PRODUCT VISION

HackathonOS is a personal Hackathon Command Center.

Its purpose is to reduce the time wasted on research, tool selection, architecture decisions, implementation failures, testing, and submission preparation.

The system should help its owner make better decisions under severe time pressure.

The core optimization objective is:

Maximize judging alignment, differentiation, execution reliability, and demo impact per available hour.

The system cannot guarantee winning, accurately predict unknown judge preferences, or claim that a project is unique without sufficient evidence.

It must maximize controllable factors and communicate uncertainty honestly.

Primary outcomes

1. Understand the competition quickly.
2. Extract official requirements accurately.
3. Research relevant solutions and opportunities.
4. Select the strongest feasible track or problem.
5. Generate and critically evaluate candidate ideas.
6. Create a time-aware implementation plan.
7. Generate context-aware coding-agent tasks.
8. Integrate with supported development tools.
9. Preserve progress across model or tool failures.
10. Test real application behavior.
11. Detect security and reliability risks.
12. Deploy and verify the actual product.
13. Create an impressive, truthful demonstration.
14. Prepare a persuasive pitch and complete submission.
15. Learn from every competition.

2. OPERATING PRINCIPLES

Implement these principles throughout the product.

2.1 Evidence before assumptions

Every important competition claim should have a source where possible.

Distinguish:

* VERIFIED FACT
* INFERENCE
* HYPOTHESIS
* UNKNOWN

Do not fabricate sources, repository activity, APIs, judge preferences, competitor capabilities, model performance, test results, or integration status.

2.2 Score per hour

Prioritize work based on expected improvement in judging alignment, user value, differentiation, reliability, and demo quality relative to its time cost.

2.3 One recommended decision

For major decisions, show:

* Recommended option.
* Reasoning.
* Evidence.
* Confidence.
* One backup.
* Conditions that justify changing the recommendation.

Avoid overwhelming the user with endless alternatives.

2.4 Small, verified implementation tasks

Use:

SPECIFY → PLAN → IMPLEMENT → RUN → VERIFY → COMMIT.

Never trust an AI coding agent’s claim that a feature works without appropriate verification.

2.5 Honest automation

Clearly distinguish:

* Proposed.
* Ready to execute.
* Running.
* Completed.
* Verified.
* Failed.
* Blocked.
* Requires approval.

Generating a plan is not execution. Executing a command is not proof of success. A successful build is not proof that the user journey works.

2.6 Reliable fallbacks

Important workflows must have explicit recovery paths when a model, provider, tool, API, network connection, or deployment service fails.

2.7 No unnecessary tool switching

Do not replace a working tool simply because another tool is trending.

Evaluate switching cost, reliability, capability, integration effort, and remaining time.

3. USER AND PRIVACY MODEL

Initially, this is a single-user application for its owner.

Do not build unnecessary multi-tenant SaaS functionality.

However, implement proper authentication and authorization so that private information is not exposed.

Requirements:

* Private authenticated workspace.
* Server-side authorization on protected operations.
* Secure session handling.
* Secure secret storage.
* Restricted repository access.
* Explicit consent for local execution.
* Explicit approval for consequential actions.
* Audit records for important operations.
* Safe handling of uploaded files.
* No public access to private projects or research.
* No secrets in browser bundles, client logs, Git history, or error messages.

A login screen alone does not make the application private.

If the selected hosting model cannot safely protect local credentials or execution, separate those capabilities into a local agent.

7. ADAPTIVE TRACK AND PROBLEM SELECTION

Support two operating modes.

Mode A: Assigned track

The user supplies the assigned track or problem.

The system must:

1. Extract constraints.
2. Interpret the problem.
3. Identify target users.
4. Identify unmet needs.
5. Research existing solutions.
6. Identify feasible opportunities.
7. Generate candidate ideas within the constraints.

Never recommend a solution outside the assigned requirements without clearly labeling it as out of scope.

Mode B: Selectable track

The user supplies the available tracks.

The system evaluates each track against:

* Judging alignment.
* Problem importance.
* Differentiation opportunity.
* Technical feasibility.
* Team skills.
* Available time.
* Data availability.
* API availability.
* Likely implementation risk.
* Demo potential.
* Existing solution maturity.
* Evidence quality.

Generate a comparative scorecard.

Use configurable weights derived from the actual competition rubric.

Do not claim to know competitor strength or judge preferences without evidence.

Recommend one primary track and one alternative when appropriate.

Explain the trade-offs.

8. DEEP RESEARCH LAB

Research is a core product capability.

Create a research workspace with source-backed findings and a clear decision trail.

* Official competition requirements.
* User pain points.
* Existing products.
* Open-source repositories.
* GitHub issues and pull requests.
* Technical documentation.
* Research papers.
* Relevant datasets.
* Available APIs.
* Alternative architectures.
* Previous winners.
* Existing implementation patterns.
* Common solution approaches.
* Product gaps.
* Technical feasibility.
* Relevant risks.
* Possible differentiation opportunities.

Source hierarchy

Prioritize:

1. Official competition documents.
2. Official product and API documentation.
3. Primary research papers and technical reports.
4. Official repositories and release documentation.
5. Reliable technical publications.
6. Community discussions where useful.

Community opinions should not automatically be treated as facts.

Research result model

Each finding should store:

* Finding title.
* Summary.
* Source URL.
* Source title.
* Source type.
* Retrieval time.
* Relevant quotation or excerpt when useful and permitted.
* Interpretation.
* Confidence.
* Fact/inference/hypothesis/unknown classification.
* Relevance to the competition.
* Related idea or decision.

Cite sources next to claims in generated reports.

Do not generate fake citations.

If live browsing is unavailable, disclose the limitation and work with provided materials.

Competitor analysis

For each relevant alternative, record:

* Product or repository name.
* Official source.
* Target users.
* Main capabilities.
* Relevant technical approach.
* Strengths.
* Limitations supported by evidence.
* Overlap with the proposed idea.
* Potential opportunity.

Do not assume a feature is missing just because it is not immediately visible in a search result.

Research stop condition

Research should stop when the team has enough evidence to make a defensible decision.

Required conditions:

* Problem is understood.
* Target user is defined.
* Judging criteria are mapped.
* Important alternatives are identified.
* Technical feasibility is assessed.
* Major unknowns are documented.
* Differentiation hypotheses are identified.
* A candidate idea can be selected.

For very short hackathons, allow a smaller but explicitly labeled evidence set.

The system should show:

* Research time used.
* Important findings.
* Unresolved unknowns.
* Recommended decision.
* Whether to continue research or begin implementation.

Never allow research to consume the entire hackathon by default.

10. ADAPTIVE WORKFLOW PLANNER

This is a central differentiator.

The system must generate a realistic plan based on:

* Available duration.
* Actual deadline.
* Research complexity.
* Number of tracks and problems.
* Team size.
* Team skills.
* Idea complexity.
* Required deliverables.
* Expected integration effort.
* Model and tool availability.
* Deployment requirements.
* Current progress.
* Known risks.
* Required demo and presentation time.

Support any custom duration, including:

3, 4, 6, 10, 12, 24, 36, and 48 hours.

These are examples, not a fixed list.

Planning algorithm

1. Calculate actual available time.
2. Identify hard deadlines.
3. Identify mandatory deliverables.
4. Estimate phase effort.
5. Account for dependencies.
6. Include testing, deployment, demo, and submission buffers.
7. Allocate research time according to uncertainty and duration.
8. Allocate build time according to product complexity.
9. Add contingency based on risk.
10. Produce a feasible schedule.
11. Ask for confirmation when major assumptions affect feasibility.

The schedule must not allocate 100% of the time to coding.

Workflow phases

Use these as adaptable building blocks:

1. Intake.
2. Problem understanding.
3. Research.
4. Track selection when needed.
5. Idea generation.
6. Idea red team.
7. Idea lock.
8. Product specification.
9. Architecture.
10. Model and tool selection.
11. Implementation.
12. Testing.
13. Security.
14. Deployment.
15. Adversarial verification.
16. Demo preparation.
17. Pitch preparation.
18. Submission audit.
19. Final review.
20. Submission.
21. Post-hackathon learning.

The planner may merge or simplify phases for very short events.

It must never remove essential competition requirements merely to make the plan appear feasible.

Task structure

Every task should contain:

* Title.
* Description.
* Phase.
* Priority.
* Estimated duration.
* Deadline.
* Dependencies.
* Owner.
* Status.
* Acceptance criteria.
* Expected artifact.
* Verification method.
* Risk if skipped.

Live replanning

When time changes or a task fails:

1. Recalculate remaining time.
2. Identify the critical path.
3. Preserve mandatory deliverables.
4. Protect testing and demo time.
5. Remove or defer low-value features.
6. Reprioritize tasks.
7. Explain what changed and why.
8. Display one next action.

Never silently overwrite the previous plan. Preserve meaningful plan versions.

5. Switch to a configured fallback if appropriate.
6. Preserve relevant context.
7. Tell the user what changed.

Never restart the project merely because the model changed.

Local execution agent

For local operations, design a separate authenticated local agent.

The local agent should:

* Bind to localhost by default.
* Authenticate requests.
* Pair securely with the private web application.
* Expose a limited set of capabilities.
* Validate every requested operation.
* Restrict working directories.
* Prevent path traversal.
* Use command allowlists where practical.
* Require approval for risky commands.
* Log operations.
* Redact secrets.
* Enforce timeouts.
* Support cancellation.
* Never expose an unrestricted shell to unauthenticated remote callers.

Do not expose local ports publicly or create an unrestricted remote shell.

The website must not execute arbitrary code simply because an AI agent requests it.

Approval gates

Require explicit approval for actions such as:

* Running unfamiliar commands.
* Deleting files.
* Installing packages.
* Modifying secrets.
* Changing access controls.
* Pushing code.
* Opening a pull request.
* Deploying production changes.
* Modifying production data.

Make approval requirements configurable within safe limits.

2. Validate permissions and inputs.
3. Record the intended operation.
4. Execute through the appropriate integration.
5. Record progress events.
6. Persist intermediate results.
7. Enforce timeouts and resource limits.
8. Handle cancellation.
9. Recover safely from retryable errors.
10. Store final output and evidence.

Prevent duplicate actions caused by retries where practical.

Use idempotency keys for appropriate operations.

Make job progress observable in the interface.

Do not hold an HTTP request open indefinitely for a long-running agent.

Do not allow agents to execute unrestricted chains of actions without permission boundaries.

⸻

25. ADAPTIVE AUTOMATION LEVELS

Support three operating modes.

MANUAL

The system researches, plans, generates prompts, and gives instructions. The user executes tasks manually.

ASSISTED

The system integrates with supported tools, retrieves results, tracks progress, and requests approval for consequential actions.

AUTONOMOUS WITH GUARDRAILS

The system executes approved low-risk workflows and verifies results. High-impact operations still require authorization.

The user must be able to change the mode.

The system must disclose which actions are truly automated and which require manual intervention.

Never fake an integration.

28. ACCEPTANCE CRITERIA

The application is not complete merely because the pages render.

Competition workflow

* A user can create a competition.
* A user can enter or upload problem information.
* Extracted requirements can be reviewed.
* Competition data persists after refresh.
* A user can resume the workspace.

Track and idea workflow

* Assigned-track mode works.
* Track-selection mode works.
* Candidate ideas are saved.
* Scores have explanations.
* Research claims link to real sources where available.
* The user can override recommendations.

Planning workflow

* Arbitrary durations are supported.
* The schedule respects the actual deadline.
* Mandatory deliverables are preserved.
* Tasks have dependencies and acceptance criteria.
* Replanning responds to changed time or failed tasks.
* Previous plan versions are preserved.

Agent workflow

* Coding tasks contain relevant context.
* The system distinguishes manual prompts from executed tasks.
* Supported integrations report actual results.
* Tool failures preserve project state.
* Risky operations require appropriate authorization.

Quality workflow

* Test results are based on actual execution.
* Security findings are recorded.
* Failed checks are visible.
* Production verification is distinct from local verification.

Submission workflow

* Official requirements can be checked.
* Missing deliverables are visible.
* The user can mark and verify submission status.
* The system does not fabricate submission confirmation.

Security

* Private data is protected.
* Authorization is checked server-side.
* Secrets are not exposed to the browser.
* Uploaded content is treated as untrusted.
* Local execution is restricted.
* Destructive operations require appropriate approval.

29. DEVELOPMENT RULES

Follow these rules during implementation.

1. Use TypeScript and strict typing where appropriate.
2. Validate inputs at system boundaries.
3. Keep provider integrations behind clear interfaces.
4. Use database migrations.
5. Add tests for important business logic.
6. Use meaningful error handling.
7. Avoid hardcoded secrets.
8. Avoid fake data presented as real execution results.
9. Avoid placeholder buttons in completed features.
10. Keep components maintainable.
11. Avoid giant files and tightly coupled modules.
12. Avoid unnecessary dependencies.
13. Record architectural decisions.
14. Use small, logical commits.
15. Do not overwrite unrelated changes.
16. Do not claim tests passed unless they ran.
17. Do not disable security controls to make a test pass.
18. Preserve backward compatibility where practical.
19. Use accessible UI patterns.
20. Keep documentation synchronized with actual behavior.

If a feature cannot be completed because credentials, infrastructure, or external capabilities are missing, implement the safe interface, document the exact limitation, and provide the best usable fallback.

FINAL PRODUCT STANDARD

HackathonOS must function as a personal competition execution system.

The core loop is:

UNDERSTAND → RESEARCH → DECIDE → PLAN → BUILD → VERIFY → IMPROVE → DEMONSTRATE → SUBMIT → LEARN

Its value is not the number of AI agents or the number of features.

Its value is helping the user spend less time on low-value work, make better product decisions, avoid preventable engineering failures, and deliver a more convincing, reliable hackathon project.

Build for real use, honest verification, privacy, maintainability, and adaptation to different competitions.

Start with repository discovery and then implement the smallest complete, working foundation.
